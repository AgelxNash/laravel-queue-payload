# Security Policy

## Поддерживаемые версии

| Версия | Поддержка          |
| ------ | ------------------ |
| 1.x    | ✅ Активная         |

## Сообщение об уязвимости

Если вы обнаружили уязвимость безопасности в этом пакете, пожалуйста:

1. **НЕ создавайте публичный Issue** — это может подвергнуть пользователей риску
2. Отправьте описание уязвимости на email разработчика
3. Укажите:
   - Тип уязвимости
   - Полное описание и шаги воспроизведения
   - Версию пакета
   - Версию PHP и Laravel
   - Потенциальное влияние (CVSS score если возможно)

## Известные риски безопасности

### 1. Произвольная инстанциация классов

По умолчанию пакет разрешает вызов любого алиаса/FQCN из Laravel Container через payload очереди. Если злоумышленник имеет write-доступ к RabbitMQ, он может инстанциировать произвольные классы.

**Митигация:** Настройте `allowed_jobs` в `config/agelxnash-queue.php`:

```php
'allowed_jobs' => [
    'TASK_CHECK_TARIFF' => \App\Jobs\CheckUserTariffJob::class,
],
```

### 2. Инъекция через параметры payload

Параметры из `data.params` передаются напрямую в конструктор Job. Пакет не валидирует входящие данные.

**Митигация:**
- Используйте type-hinted параметры: `private readonly int $userId`
- Валидируйте данные в `handle()` методе
- Для строгой валидации используйте DTO

### 3. Подделка correlation ID

При read-доступе к RabbitMQ злоумышленник может увидеть correlationId и подделать ответ.

**Митигация:**
- Используйте TLS для соединений с RabbitMQ
- Ограничьте read/write доступ к очередям на уровне RabbitMQ ACL
- Валидируйте структуру входящих ответов

### 4. Race condition в persistent-средах

В средах с persistent процессами (Swoole, RoadRunner, Octane) параллельные RPC-вызовы могут перезаписать состояние `ResponseHandler`.

**Митигация:** В классическом PHP-FPM это не проблема (один запрос = один процесс). Для persistent-сред рекомендуется создавать новый `ResponseHandler` на каждый вызов.

## Рекомендации по production-развёртыванию

1. ✅ Настройте `allowed_jobs` в конфиге
2. ✅ Используйте TLS для RabbitMQ соединений
3. ✅ Ограничьте доступ к очередям через RabbitMQ ACL
4. ✅ Валидируйте входящие параметры в каждой Job
5. ✅ Мониторьте очередь ответов на наличие аномалий
6. ✅ Установите разумный `QUEUE_RESPONSE_TIMEOUT` (не бесконечный)
7. ✅ Регулярно обновляйте зависимости (`composer update`)
